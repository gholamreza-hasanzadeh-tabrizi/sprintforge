## ۴) یافته‌ها (به ترتیب شدت)

### 🔴 P1 — دکمهٔ «···» داده را بدون هیچ تأییدی پاک می‌کند
`src/pages/project-page/project-page.tsx:166` و `:187`

```tsx
const resetDemo = useCallback(() => { setIssues(initialIssues); localStorage.removeItem(...) }, ...)
...
<Button variant="ghost" size="icon" aria-label="Restore sample data" title="Restore sample data" onClick={resetDemo}>
  <MoreHorizontal size={18}/>
</Button>
```

آیکون «···» در هدر صفحه، در واقع **ریست کامل داده** است: یک کلیک اشتباهی، همهٔ کامنت‌ها/ساب‌تسک‌ها/تغییرات را بی‌بازگشت پاک می‌کند. نه `Dialog` تأیید دارد، نه undo، نه حتی آیکون درست (سه‌نقطه یعنی «گزینه‌های بیشتر»).
پیشنهاد: حذف این دکمه از هدر و نگه‌داشتن عمل بازگردانی فقط در Settings، آن هم با دیالوگ تأیید.

### 🔴 P1 — فیلتر آمادهٔ «High priority» هم ناقص است هم ناسازگار
`src/components/organisms/filters-view/filters-view.tsx:28`

خروجی واقعی (اجرا کردم):

```
High priority  => NOVA-128, NOVA-119, NOVA-130, NOVA-111, NOVA-121   (۵ مورد)
Needs review   => NOVA-122, NOVA-130                                  (۲ مورد)
Due in 7 days  => NOVA-128, NOVA-119, NOVA-143                        (۳ مورد)
My open issues => NOVA-134                                            (۱ مورد)
```

دو ایراد:
1. `priority: 'High'` مقایسهٔ **تساوی دقیق** است، پس `NOVA-143` با اولویت `Highest` بیرون می‌ماند — کاربر «High priority» را می‌زند و مهم‌ترین باگ باز پروژه غایب است.
2. همین فیلتر `openOnly` ندارد، پس دو تسک `done` (`NOVA-111`, `NOVA-121`) هم داخلش هستند، در حالی که سه فیلتر آمادهٔ دیگر کارهای بسته را حذف می‌کنند. یعنی یک فیلتر «آماده» با بقیه هم‌قاعده نیست.

### 🟠 P2 — فیلتر فعال برای صفحه‌خوان اعلام نمی‌شود
`filters-view.tsx:93` — انتخاب فیلتر فقط با کلاس CSS (`bg-primary/10`) نشان داده می‌شود؛ `aria-pressed`/`aria-current` روی دکمه‌ها نیست. استاندارد درون همین مخزن (`WatchButton`, `SubtaskList`) از `aria-pressed` استفاده می‌کند، پس این انحراف از الگوی خودِ پروژه است.

### 🟠 P2 — فیلد `query` در اسکیما مرده است
`types/domain/filter.ts` + `filters-view.tsx:78`

`SavedIssueFilter.query` همیشه `''` ساخته می‌شود و هیچ ورودی UI برای پر کردنش وجود ندارد، اما `matchesFilter` کد جست‌وجوی متنی برای آن دارد. یعنی: قابلیت پیاده‌سازی شده، ولی از UI قابل استفاده نیست؛ در حالی که placeholder فرم («e.g. Aisha’s high-priority work») وعدهٔ جست‌وجوی متنی می‌دهد. یا ورودی «Search text» اضافه شود یا فیلد از تایپ حذف شود.

### 🟠 P2 — اعتبارسنجی `localStorage` سطحی است: فیلتر «بی‌صدا خالی» ممکن می‌شود
`filters-view.tsx:33-39`

فقط نوع `string` بودن چک می‌شود، نه معتبر بودن مقدار. تست کردم با دادهٔ ذخیره‌شدهٔ `status: 'nope'`:

```
عنوان فیلتر: Broken  →  «0 matching issues»
```

بدون هیچ پیام خطا یا پیشنهادی. اگر روزی یکی از `IssueStatus`ها تغییر نام دهد، فیلترهای ذخیره‌شدهٔ کاربر بی‌صدا بی‌اثر می‌شوند.
همچنین `JSON` خراب بی‌صدا به `[]` تبدیل و **بلافاصله بازنویسی** می‌شود (`:72`) — یعنی دادهٔ خرابِ قابل بازیابی، دور ریخته می‌شود.

### 🟠 P2 — نام تکراری فیلتر مجاز است و برچسب‌های دسترس‌پذیری را تکراری می‌کند
دو فیلتر هم‌نام «Dup» ساختم → دو دکمهٔ `aria-label="Delete Dup"`. نتیجه: نام دسترس‌پذیری غیریکتا، و همچنین «کدام فیلتر فعال است؟» برای کاربر مبهم. همچنین هیچ سقف تعداد یا امکان تغییرنام وجود ندارد.

### 🟠 P2 — خروجی CSV دو اشکال عملی دارد
`src/components/organisms/reports-view/reports-view.tsx:33-43`

```tsx
link.click(); link.remove(); URL.revokeObjectURL(url)
```

1. `revokeObjectURL` **بلافاصله** بعد از کلیک صدا زده می‌شود؛ در Firefox و بعضی نسخه‌های Safari این کار دانلود را می‌شکند (الگوی درست: `setTimeout(..., 0)` یا آزادسازی بعد از رویداد `load`).
2. BOM یونیکد (`\uFEFF`) در ابتدای فایل نیست، پس Excel با متن‌های غیرلاتین/گیومه‌های تایپوگرافی درست رفتار نمی‌کند. ضمناً ستون Status مقدار خام (`progress`) صادر می‌شود نه برچسب (`In progress`).

### 🟡 P3 — «Restore sample data» فیلترهای ذخیره‌شده را بازنمی‌گرداند
کارت دادهٔ دمو در `SettingsView` می‌گوید «Issues, comments, watchers, subtasks, and **saved filters** are stored only in this browser»، ولی `resetDemo` فقط کلید `sprintforge-issues-v1` را پاک می‌کند و کلید `sprintforge-saved-filters-v1` دست‌نخورده می‌ماند. یا متن دقیق‌تر شود یا کلید فیلترها هم پاک شود.

### 🟡 P3 — دو منبع حقیقت برای فیلتر کردن
`project-page.tsx` فیلتر جست‌وجو/مسئول/اولویت را درون خودش دارد (`filteredIssues`) و `FiltersView` هم `matchesFilter` مستقل خودش را. هر تغییر در معنای فیلتر باید در دو جا انجام شود. منطق مشترک باید به `src/lib/filters.ts` یا یک هوک برود.

### 🟡 P3 — تکرار سه‌بارهٔ تابع تاریخ و هاردکد شدن کاربر جاری
- تابع ساخت `YYYY-MM-DD` محلی در `calendar-view.tsx:8`، `my-work-view.tsx:14` و `filters-view.tsx:41-44` سه بار کپی شده.
- `FiltersView` نام `'Olivia Chen'` را داخل preset هاردکد کرده، در حالی که `MyWorkView` الگوی درست را دارد: `currentUser = 'Olivia Chen'` به‌عنوان prop با مقدار پیش‌فرض. بهتر است `FiltersView` هم `currentUser` بگیرد.

### 🟡 P3 — وضعیت `localStorage` مدیریت‌نشده است
`filters-view.tsx:72` بدون `try/catch` نوشتن انجام می‌دهد. در حالت‌های مسدود/سرریز (Safari حالت خصوصی، سهمیهٔ پر) خطای داخل افکت، کل درخت React را می‌شکند؛ و چون پروژه Error Boundary ندارد، صفحه سفید می‌شود.

### 🟡 P3 — ARIA تب‌ها نامعتبر است
`project-page.tsx:188`: نُه دکمه با `role="tab"` داخل یک `div` بدون `role="tablist"` و بدون `aria-controls`/`tabpanel`؛ همچنین دکمهٔ «+» (`aria-label="Open saved filters"`) داخل نوار تب‌ها نشسته که هم از نظر نقش و هم از نظر معنا (پلاس = ساخت) گمراه‌کننده است. الگوی درست در همین مخزن در `issue-dialog.tsx:62` پیاده شده است.

### 🟡 P3 — پوشش تست نسبت به ادعا کم است
تست‌های اضافه‌شده: `filters-view.test.tsx` (۲ تست)، `settings-view.test.tsx` (۱ تست)، `reports-view.test.tsx` (۲ تست). آنچه تست ندارد:

- حالت خالی («No issues match this filter»)
- حذف فیلترِ فعال و بازگشت به preset
- مرزهای «Due in 7 days» (سررسید امروز / گذشته)
- `SettingsView`: متن واقعی دکمهٔ تم بعد از کلیک، نه فقط صدا زده شدن callback

### 🟡 P3 — قالب‌بندی و نگهداشت‌پذیری
کل UI هر ویو در یک خط JSX چند هزار کاراکتری است (`filters-view.tsx:92-99`). این کار review و diff را عملاً غیرممکن می‌کند و علت مستقیم اینکه باگ‌های بالا با چشم پیدا نمی‌شوند همین است. (این الگو در `project-page.tsx` هم هست، پس مشکل تازه نیست، ولی این کامیت ۱۰۱ خط تازه از همان جنس اضافه کرده.)
